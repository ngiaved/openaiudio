# ADR 0001 · Hybrid topology for simultaneous transcription and translation

- Status: **Accepted** (v0.1)
- Date: 2026-09
- Category: Server architecture

## Context

OpenAIudio transcribes and translates conference talks in real time (several
stages in parallel). We need a topology that:

1. Produces the **original** transcript with low latency and without depending
   on a local GPU.
2. **Translates** into several languages with providers that differ by
   environment (Gemini/AI Studio in the cloud, Gemma via Ollama fully local).
3. Tolerates network drops and rate limits without losing the talk.
4. Runs on a single production laptop with no cluster complexity.

## Options considered

### A. All by audio (Gemini Live only)
Stream audio bytes to the cloud for the original and for every translation
(one stream per language). Very simple, best intonation quality, but requires
stable connectivity and high API usage.

### B. All by local text (whisper + Gemma)
Original with local `faster-whisper` and translation with Gemma via Ollama.
Fully offline, but latency and quality depend on the laptop's hardware.

### C. Hybrid (chosen)
- The **original** is always generated from audio (Gemini windowed STT or
  local whisper).
- **Translations** are generated by **audio** (Gemini Live, streaming) or by
  **text** (Gemini text model or Gemma/Ollama), configurable per session.
- `auto` mode: audio only for mock (demo); text for Gemini and local (see note
  below).

## Decision

Topology **C** is adopted. Each session declares `provider` and
`translation_mode` (`audio | text | auto`); the orchestrator (`app/store.py`)
decides the pathway of the original (always audio) and of each translation,
and keeps an active-provider budget (config-capped) with promotion to `live`
when audio arrives and demotion to `idle` under the idle sweeper.

## Consequences

Positive:
- One server tolerates cloud signals and 100 % local signals alike.
- `provider=auto` lets you start a demo without an API key using `mock`.
- Original latency is independent of translation.

Negative:
- Two different quality paths for translation (audio vs text).
- The text provider retries with backoff; the first text translation may take
  longer to start than the audio one.

Note on `auto` mode (revised after testing with a real API key):
- The Gemini original uses **windowed** STT (audio `generate_content` +
  text), not Live streaming: the `*-transcribe-live` models are preview and
  unstable, and the windowed pathway is robust and cheap.
- `auto` resolves to: **audio** only for mock (demo); **text** for Gemini
  (translation) and local. The Live (audio) pathway stays available explicitly
  via `TRANSLATION_MODE=audio` and `GEMINI_LIVE_MODEL`.
